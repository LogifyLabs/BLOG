# Logify Method: 본질 중심 사고법
**5단계로 문제의 핵심을 꿰뚫다**

**Tags:** #Logify #문제해결 #사고법 #본질 #방법론

---

## TL;DR

```
문제를 만나면:
1. 전제: 올바른 질문인가?
2. 본질: 진짜 원인은?
3. 구조화: 논리가 명확한가?
4. 검증: 비약은 없나?
5. 실행: 어떻게 움직일까?

= Logify Method
```

---

## 시작하며: 우리는 표면만 본다

**일상의 문제 해결:**

```
문제: 프로젝트가 늦어진다
해결: 야근한다
결과: 다음 프로젝트도 늦어진다

문제: 매출이 떨어진다
해결: 광고를 늘린다
결과: 비용만 증가한다

문제: 팀 분위기가 안 좋다
해결: 회식한다
결과: 일시적 기분만 좋아진다
```

**왜 이럴까?**

→ 우리는 **표면의 증상**만 다루고, **본질의 원인**은 보지 못합니다.

**Logify Method는 이 문제를 해결합니다.**

---

## Logify가 뭔가요?

### 한 줄 정의

> 5단계로 문제의 본질을 찾고, 구조화하고, 실행하는 사고 프레임워크

### 핵심 철학

1. **본질 중심 (Essence-First)**
   - 표면이 아닌 근본
   - 증상이 아닌 원인
   - What이 아닌 Why

2. **구조화된 사고 (Structured Thinking)**
   - 직관 → 논리로
   - 모호함 → 명확함으로
   - 혼돈 → 질서로

3. **실행 지향 (Action-Oriented)**
   - 생각 → 행동으로
   - 분석 → 실천으로
   - 이론 → 현실로

## 왜 Logify인가?

### 기존 방법론의 한계

#### 5 Whys (도요타)
```
✅ 장점: 간단, 빠름
❌ 한계: 
- 어디서 멈춰야 할지 모름
- 구조화 안 됨
- 검증 없음
```

#### MECE (컨설팅)
```
✅ 장점: 논리적, 체계적
❌ 한계:
- 너무 복잡
- 본질 놓침
- 실행 약함
```

#### First Principles (엘론 머스크)
```
✅ 장점: 근본적, 혁신적
❌ 한계:
- 너무 추상적
- 적용 어려움
- 시간 많이 걸림
```

### Logify의 차별점

```
5 Whys의 심플함
+
MECE의 구조화
+
First Principles의 본질 추구
+
즉시 실행 가능

= Logify Method
```

## 5단계 프로세스

### 전체 흐름

```
문제 발생
  ↓
1. 전제: 올바른 질문?
  ↓
2. 본질: 진짜 원인?
  ↓
3. 구조화: 논리 명확?
  ↓
4. 검증: 비약 없나?
  ↓
5. 실행: 어떻게?
  ↓
해결!
```

---

## Step 1: 전제 (Premise)

> "올바른 질문을 하고 있는가?"

### 핵심 질문

```
❌ 잘못된 질문:
"어떻게 더 빨리 할까?"
"어떻게 비용을 줄일까?"
"어떻게 더 팔까?"

✅ 올바른 질문:
"이게 진짜 해결해야 할 문제인가?"
"문제를 잘못 정의하고 있진 않나?"
"더 근본적인 질문은 없나?"
```

### 전제 체크리스트

```
□ 이게 진짜 문제인가?
□ 누구의 관점에서 문제인가?
□ 왜 지금 해결해야 하나?
□ 해결하면 무엇이 바뀌나?
□ 숨겨진 가정은 없나?
```

### 실전 예시

**Before:**
```
문제: 웹사이트가 느리다
질문: 어떻게 속도를 올릴까?
```

**After (전제 점검):**
```
전제 질문:
- 사용자가 정말 속도 때문에 이탈하나?
- 다른 이유는 없나?
- 속도가 핵심 문제인가?

→ 분석 결과: 이탈률 높은 페이지는 느린 페이지가 아니라 
   콘텐츠가 부족한 페이지였음

→ 진짜 문제: 속도 (X) → 콘텐츠 품질 (O)
```

## Step 2: 본질 (Essence)

> "표면 아래 진짜 원인은 무엇인가?"

### 5 Whys 확장

도요타의 5 Whys를 넘어서:

```
Why 1: 증상
Why 2: 직접 원인
Why 3: 구조적 원인
Why 4: 시스템 원인
Why 5: 근본 원인
```

### 본질 추적 프로세스

```
1. 증상 파악
   → "무엇이 보이는가?"

2. 직접 원인
   → "무엇이 이를 일으켰나?"

3. 구조적 원인
   → "왜 그런 일이 가능했나?"

4. 시스템 원인
   → "어떤 시스템이 이를 만들었나?"

5. 근본 원인
   → "근본적으로 무엇이 문제인가?"
```

### 실전 예시

**문제: 프로젝트가 2주 지연됨**

```
Why 1 (증상):
버그가 너무 많았다

Why 2 (직접 원인):
테스트가 부족했다

Why 3 (구조적 원인):
일정이 너무 타이트해서 테스트 시간이 없었다

Why 4 (시스템 원인):
영업이 고객에게 비현실적 일정을 약속했다

Why 5 (근본 원인):
개발팀과 영업팀의 소통 구조가 없다
+ 영업 인센티브가 '계약'에만 몰려있다

→ 진짜 해결책: 테스트 시간 늘리기 (X)
                조직 소통 구조 만들기 + 인센티브 재설계 (O)
```

### 주의사항

```
⚠️ 멈추지 마세요:
- "테스트가 부족했다"에서 멈추면
  → 테스트만 늘리고 끝
  → 다음 프로젝트도 지연

✅ 끝까지 파세요:
- "조직 구조가 문제"까지 가면
  → 근본 해결
  → 재발 방지
```

## Step 3: 구조화 (Structure)

> "생각을 명확한 논리로 정리했는가?"

### 구조화의 목적

```
혼란스러운 생각
  ↓
명확한 논리
  ↓
공유 가능한 형태
```

### 구조화 도구

#### 1. 인과 관계 (Causality)

```
A → B → C

예:
소통 부재 → 비현실적 일정 → 테스트 부족 → 버그 → 지연
```

#### 2. 계층 구조 (Hierarchy)

```
근본 원인
  ├─ 구조적 원인 1
  │   ├─ 증상 1-1
  │   └─ 증상 1-2
  └─ 구조적 원인 2
      ├─ 증상 2-1
      └─ 증상 2-2
```

#### 3. 순환 구조 (Loop)

```
A → B → C → A (강화 루프)

예:
테스트 부족 → 버그 많음 → 수정 시간 증가 
→ 테스트 시간 더 부족 → (반복)
```

### 실전 방법

#### 종이 + 펜
```
1. 원인들을 모두 적는다
2. 화살표로 연결한다
3. 패턴을 찾는다
4. 핵심만 남긴다
```

#### 옵시디언
```
1. 각 원인을 노트로 만든다
2. [[링크]]로 연결한다
3. 그래프 뷰로 본다
4. 구조를 파악한다
```

#### 화이트보드
```
1. 팀과 함께 그린다
2. 실시간 수정한다
3. 사진 찍는다
4. 문서화한다
```

## Step 4: 검증 (Verification)

> "논리적 비약은 없는가?"

### 검증 체크리스트

#### 1. 전제 검증
```
□ 전제가 사실인가?
□ 증거가 있나?
□ 반례는 없나?
```

#### 2. 논리 검증
```
□ A → B가 성립하나?
□ 다른 원인은 없나?
□ 인과관계가 명확한가?
```

#### 3. 결론 검증
```
□ 결론이 논리적인가?
□ 과잉 일반화는 없나?
□ 실행 가능한가?
```

### 흔한 오류

#### 1. 상관관계 ≠ 인과관계

```
❌ 잘못된 추론:
"A와 B가 함께 증가한다 → A가 B의 원인이다"

예: 
아이스크림 판매 ↑ + 익사 사고 ↑
→ 아이스크림이 익사 원인? (X)
→ 진짜 원인: 여름 (날씨)
```

#### 2. 확증 편향

```
❌ 위험:
내 생각을 지지하는 증거만 찾기

✅ 대응:
"이게 틀렸다면?" 반문하기
반례 적극적으로 찾기
```

#### 3. 단순화의 함정

```
❌ 위험:
복잡한 문제를 단일 원인으로 환원

✅ 현실:
대부분 문제는 다중 원인
시스템적 상호작용
```

## Step 5: 실행 (Execution)

> "사고를 행동으로 전환하는가?"

### 실행 프레임워크

```
분석 완료
  ↓
우선순위 결정
  ↓
구체적 액션
  ↓
책임자 지정
  ↓
일정 수립
  ↓
실행!
```

### 우선순위 매트릭스

```
영향력 (Impact)
  ↑
  │ 2순위  │ 1순위
  │────────┼────────
  │ 4순위  │ 3순위
  └──────────────→
         실행 난이도 (Ease)

1순위: 큰 영향 + 쉬움 → 즉시 실행
2순위: 큰 영향 + 어려움 → 계획 후 실행
3순위: 작은 영향 + 쉬움 → 여유 있을 때
4순위: 작은 영향 + 어려움 → 보류/폐기
```

### 액션 템플릿

```
## 근본 원인
[Step 2에서 찾은 것]

## 해결 방안
[구체적 액션들]

## 우선순위
| 액션 | 영향력 | 난이도 | 순위 |
|------|--------|--------|------|
| A    | 높음   | 낮음   | 1    |
| B    | 높음   | 높음   | 2    |
| C    | 낮음   | 낮음   | 3    |

## 실행 계획
- [ ] 액션 A (담당: 홍길동, 기한: 10/20)
- [ ] 액션 B (담당: 김철수, 기한: 11/15)
- [ ] 액션 C (담당: 이영희, 기한: 12/01)

## 성공 지표
- KPI 1: ___
- KPI 2: ___
- 측정 방법: ___
```

## 실전 적용 사례

### Case 1: 개인 의사결정

**상황: 이직을 고민 중**

```
Step 1 (전제):
질문: "어떤 회사로 갈까?"
→ "이직이 정답인가?" (전제 재검토)

Step 2 (본질):
Why 1: 현재 회사가 불만족스럽다
Why 2: 성장이 느리다
Why 3: 도전적 프로젝트가 없다
Why 4: 내가 요청하지 않았다
Why 5: 요청할 용기가 없었다

→ 근본 원인: 수동적 태도

Step 3 (구조화):
수동적 태도 → 요청 안 함 → 기회 없음 
→ 성장 정체 → 불만 → 이직 고민

Step 4 (검증):
- 이직하면 해결? → 아닐 수도
- 다른 회사에서도 수동적이면 반복
- 진짜 해결: 태도 변화

Step 5 (실행):
1순위: 리더에게 도전적 프로젝트 요청
2순위: 사내 새 프로젝트 제안
3순위: 이직 준비 (위 둘 시도 후)
```

### Case 2: 팀 문제 해결

**상황: 회의가 비효율적**

```
Step 1 (전제):
질문: "회의를 어떻게 개선할까?"
→ "회의가 필요한가?" (전제 재검토)

Step 2 (본질):
Why 1: 회의가 길다
Why 2: 논점이 산만하다
Why 3: 목적이 불명확하다
Why 4: 안건 없이 모인다
Why 5: 회의 문화가 형식적이다

→ 근본 원인: 회의 목적/구조 부재

Step 3 (구조화):
목적 부재 → 안건 없음 → 산만함 
→ 시간 낭비 → 피로도 증가

Step 4 (검증):
- 모든 회의가 문제? → 일부만
- 어떤 회의? → 정기 회의
- 왜? → 습관적으로 잡음

Step 5 (실행):
1순위: 회의 목적 명시 규칙
2순위: 안건 없으면 취소
3순위: 회의록 템플릿 도입
```

### Case 3: 프로젝트 기획

**상황: 신규 기능 개발**

```
Step 1 (전제):
질문: "어떤 기능을 만들까?"
→ "왜 이 기능이 필요한가?" (전제 점검)

Step 2 (본질):
Why 1: 고객이 요청했다
Why 2: 경쟁사에 있다
Why 3: 우리도 있어야 한다
Why 4: 고객을 잃을까 봐
Why 5: 우리만의 강점이 불명확하다

→ 근본 원인: 차별화 포인트 부재

Step 3 (구조화):
차별화 없음 → 경쟁사 따라하기 
→ Me-too 기능 양산 → 리소스 낭비

Step 4 (검증):
- 이 기능이 차별화? → 아님
- 진짜 필요? → 불명확
- 다른 방법? → 기존 강점 강화

Step 5 (실행):
1순위: 우리 강점 재정의
2순위: 강점 강화 기능 개발
3순위: Me-too 기능은 보류
```

## 자주 묻는 질문

### Q1: 5 Whys랑 뭐가 다른가요?

```
5 Whys:
- 3단계: Why 반복
- 끝: 원인 파악

Logify:
- 1단계: 전제 점검 (문제 재정의)
- 2단계: 본질 추적 (5 Whys 확장)
- 3단계: 구조화 (시각화)
- 4단계: 검증 (논리 체크)
- 5단계: 실행 (액션플랜)

→ 더 체계적, 실행까지
```

### Q2: 매번 5단계 다 해야 하나요?

```
아니요!

간단한 문제: 2-3단계만
복잡한 문제: 전체 5단계
긴급한 문제: 2+5단계 (본질+실행)

상황에 맞게 조절하세요.
```

### Q3: 혼자 해야 하나요?

```
개인 결정: 혼자
팀 문제: 함께
조직 이슈: 이해관계자 전원

협업할수록 더 강력합니다.
```

### Q4: 얼마나 걸리나요?

```
간단한 문제: 10-30분
중간 문제: 1-2시간
복잡한 문제: 반나절-하루

처음엔 느려도
익숙해지면 빨라집니다.
```

### Q5: 실패할 수도 있나요?

```
네, 있습니다.

실패 원인:
- 전제를 잘못 잡음
- 본질까지 안 감
- 검증을 스킵함
- 실행을 안 함

→ 5단계 성실히 따르면
   실패 확률 대폭 감소
```
